# 아키텍처와 네 가지 설계 원칙

## 기본 구조

```text
        업무 앱 / BI / AI / API  (L3, 활용 계층)
                 ↕       ↕
       공통 의미 모델 (L2)     독립 해석 저장소
       객체·관계·정의          개인·부서·AI의 평가
                 ↕
         공유 원천 기록 (L1)
       DB · 문서 · 로그 · 사건
```

L1과 L2는 **기업 공유 자산**이며, 해석은 별도 공간에 보관한다. 모든 접근은 보안·개인정보·권한 정책의 범위 내에서 이루어진다.

## 네 가지 원칙
1. **공유:** 원본과 공통 모델에 모두 재접근할 수 있다.
2. **독립:** 평가·추정이 공통 사실을 임의로 덮어쓰지 않는다.
3. **비례:** 재사용 빈도, 의사결정 영향, 규제 위험에 따라 관리 수준을 조정한다.
4. **추적 가능성:** 출처, 생성 맥락, 정의, 정정 및 변경 이력을 확인한다.

## 다섯 정보 유형과 검증 상태: 서로 다른 축
| information_type | 의미 |
|---|---|
| observation | 관측·기록된 사건 |
| hypothesis | 가설·추정 |
| reviewed_assessment | 검토된 평가 |
| official_decision | 조직이 채택한 공식 판단 |
| execution_result | 실제 실행과 결과 |

검증 상태는 별도 필드: `unverified`, `in_review`, `verified`, `disputed`.

이 유형들은 **순차적인 상태 전이 과정이 아니다**. 공식 판단의 존재가 확인되었다고 그 판단 내용이 객관적 진실이 되는 것도 아니다.

## 일반 기업 사례
설비가 40분 정지한 기록은 공유된다. 생산팀은 생산 차질, 정비팀은 재발 가능성, 재무팀은 손실 비용을 각각 평가한다. 평가자와 기준이 다른 값을 하나의 공식 '위험도'로 덮어쓰지 않는다.
